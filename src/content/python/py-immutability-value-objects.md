You have now met immutability from several directions: frozen dataclasses, `NamedTuple`, and the copying lesson's observation that immutable objects never need defensive copying. This lesson pulls those threads together into a single, deliberate design idea: the **value object** — a small class defined entirely by its data, with no identity that matters, and no way to change it after creation.

You will learn:

- what makes something a value object, precisely
- frozen dataclasses as the standard way to build one
- the "with-style" update: `replace`, and a hand-written `with_x`
- hashing rules for immutable objects, revisited
- thread-safety, as a free consequence of immutability
- the trap of a mutable field hiding inside a frozen object

## What makes a value object

A **value object** represents a *value* — a point in space, an amount of money, a date range — rather than a *thing with an identity* that changes over time (a bank account, a user session). Two value objects with the same data should be **interchangeable**: equal, and safely substitutable for one another anywhere.

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Point:
    x: float
    y: float

a = Point(1, 2)
b = Point(1, 2)
print(a == b, a is b)
```

`a` and `b` are different objects, but as **values**, they are the same point — which is exactly why `__eq__` (generated by `@dataclass`) compares their data, not their identity.

## frozen=True is the standard tool

`frozen=True` is what turns a dataclass from an ordinary mutable record into a genuine value object: assignment after construction raises, which is precisely the guarantee a value object should make:

<!-- expect-error -->
```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Point:
    x: float
    y: float

p = Point(1, 2)
p.x = 99
```

## The with-style update

Since you cannot mutate a value object, "changing" one means building a **new** one with some fields updated. `dataclasses.replace` does this generically:

```python
from dataclasses import dataclass, replace

@dataclass(frozen=True)
class Point:
    x: float
    y: float

p = Point(1, 2)
moved = replace(p, x=99)
print(p, moved)
```

For a class where you want a more specific, self-documenting method, write your own — this is the "`with_x`" pattern, common in codebases that favour immutability:

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Point:
    x: float
    y: float

    def with_x(self, new_x):
        return Point(new_x, self.y)

    def with_y(self, new_y):
        return Point(self.x, new_y)

p = Point(1, 2)
print(p.with_x(10))
print(p)
```

Notice `p` itself is never touched — `with_x` always returns a **new** `Point`, leaving the original exactly as it was, which is the entire point of the pattern.

## Hashing, revisited

Because a frozen dataclass generates a matching `__hash__` from the same fields as `__eq__` (unlike an ordinary mutable object, whose `__hash__` is disabled once you define `__eq__` — the contract from earlier in this section), value objects work naturally as dictionary keys and set members:

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Point:
    x: float
    y: float

visited = {Point(0, 0), Point(1, 1), Point(0, 0)}
print(len(visited))

distances = {Point(0, 0): 0, Point(1, 1): 1.41}
print(distances[Point(0, 0)])
```

`distances[Point(0, 0)]` finds the entry even though it is a **different** `Point` object from the one originally used as the key — because, as a value, it is the same point.

## Thread-safety, for free

An object that can never change after construction cannot be corrupted by two threads changing it at once — there is nothing to race over. This is one of the most practical benefits of immutability in real systems: value objects need no locks, and can be freely shared between threads (a topic explored properly in a later tier) without any extra care at all.

## The trap: a mutable field hiding inside

`frozen=True` stops you from **reassigning** a field, but it does **not** make the field's own value immutable. A frozen dataclass with a list field can still have that list mutated in place, silently breaking the "value" guarantee:

```python
from dataclasses import dataclass, field

@dataclass(frozen=True)
class Tags:
    labels: list = field(default_factory=list)

t = Tags(["a", "b"])
t.labels.append("c")
print(t.labels)
```

No error at all — `t.labels` was never *reassigned*, only *mutated*. For a true value object, every field should itself be immutable: use a `tuple` instead of a `list`, or `frozenset` instead of `set`.

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Tags:
    labels: tuple = ()

t = Tags(("a", "b"))
print(t.labels)
```

A `tuple` genuinely has no `append`, so the mistake is caught immediately, rather than silently corrupting a value that was supposed to be fixed forever.

## Common mistakes

- Believing `frozen=True` alone makes an object fully, recursively immutable — it only stops reassignment of its own fields.
- Storing a `list` or `dict` field on a frozen dataclass, and mutating it in place.
- Mutating what should be a value object because "it's just this one place", and later being unable to find where its value actually changed.

## Recap

- A value object is defined entirely by its data, with no meaningful identity of its own.
- `@dataclass(frozen=True)` is the standard way to build one; use `replace` or a hand-written `with_x` to "change" one, by making a new instance.
- Genuine immutability requires every field to be immutable too — prefer tuples and frozensets over lists and sets.
- Immutable objects are naturally hashable, and naturally safe to share.
